# AgenticSidebar — Multi-Agent Coding Platform V2 Technical Design

Date: 2026-09-18  
Status: Architecture approved by user; this technical specification and companion plan require review before implementation.  
Scope: A — software development only.  
Implementation plan: `docs/superpowers/plans/2026-09-18-multi-agent-coding-platform-v2-implementation.md`.

## 1. Product contract and non-goals

A user creates a coding objective in a native macOS board. The application decomposes it into tasks with explicit dependencies and acceptance criteria; assigns eligible agent roles and provider runtimes; executes code-changing attempts only in owned, isolated Git worktrees; runs real project-defined verification; records review findings; and places validated changes in a user approval queue. Task state, audit events and evidence survive an application restart. The user can pause, resume, stop and inspect every attempt. The existing chat workflow remains usable throughout.

**MVP outcome:** one local repository; one active code-writing attempt per repository; Architect / Developer / Reviewer / QA logical roles; OpenCode execution; a direct OpenAI **text-only** planning/summarization path with supplied bounded context but no claim of repository read or tool access; persistent task board; worktree isolation; real Swift verification; explicit review and merge/push authorization. Other provider families, parallel writers, automatic PR creation, remote execution, cloud sync, unattended merge/deploy, arbitrary computer-use automation and automatic installation of CLIs are not MVP features. Later adapter additions require separately verified contracts, not optimistic compatibility claims.

Distinguish provider (e.g. OpenAI), model, runtime (OpenCode versus direct API versus a CLI), and role. A model being selectable inside OpenCode does not make direct API execution capable of OpenCode's tool permissions or session semantics.

## 3. Module boundaries and ownership

The new `TaskBoard/` source directory owns domain, store, scheduler and task-facing application service. `ProviderGateway/` owns the neutral coding-agent contract and capability vocabulary. Existing `OpenCodeProvider/` and `OpenAIProvider/` own concrete adapters. `Workspace/` owns Git/worktree operations and ownership manifests. `Verification/` owns recipe resolution, shell-free execution, evidence and completion gates. `Views/TaskBoard/` owns SwiftUI surfaces and presentation mapping. Existing `AgentCore/`, session archive and `GoalEngine` retain their current responsibilities: board tasks do not inherit chat todo state, and a running `/goal` is not migrated or restarted. Optionally turning a goal into a new board task is an explicit, later user action.

Dependency direction: Views → `CodingTaskService` → scheduler/store + `CodingAgentRuntime` registry + workspace/verifier ports. Provider adapters and Git/process implementations conform to ports; neither views nor domain models import concrete OpenCode/OpenAI types. `AgenticSidebarApp` remains the process-lifetime composition root. Shared `PermissionApprovalCenter` handles only permission events that actually reach it; vendor configuration may pre-authorize tools before an event, and that limitation must be surfaced. Provider prompts are not a filesystem or OS security boundary. An isolated Git worktree prevents accidental edits to the main checkout; it is **not** an OS sandbox.

No service may own an unbounded background task without an explicit shutdown/cancellation path. UI-facing observable state is `@MainActor`; persistent store, scheduling and process execution live in actors. Events are bounded/backpressured. Critical state events cannot be dropped to reduce memory use.

## 4. Canonical domain and schema

`CodingProject`: UUID, canonical repository path and Git identity, project display name, protected refs, creation time. Repository identity is verified at open and before dispatch, not inferred from display name. MVP one repository selected per board.

`CodingTask`: UUID, project ID, objective, title, priority, ordered acceptance criteria with stable IDs, `TaskStatus`, `TaskStage`, monotonically increasing version, created/updated times. Task status is `backlog | ready | running | blocked | review | done | cancelled`; stage is `analysis | plan | implementation | verification | codeReview | qa | acceptance`. `blocked` includes an actionable `BlockReason`, and preserves the previous stage. The status is never inferred from textual agent output.

`TaskDependency`: directed edge `(prerequisiteTaskID, dependentTaskID)` scoped to one project; unique edge and self-edge rejection. Adding an edge performs a transactionally checked cycle test; a prerequisite is satisfied only at `done`, never merely `review`. Removing a prerequisite or reopening a task recomputes downstream readiness. MVP reopening `done` creates a new follow-up task, preserving previous evidence.

`TaskAttempt`: UUID, task ID, attempt sequence, role, provider ID, model ID and optional variant snapshot, workspace ID, generation, lease owner/token and expiry, start/end times, normalized outcome, usage fields marked unknown when not reported. Each retry creates a new attempt; attempts are immutable once finalized. `AgentProfile` binds role, eligible runtime IDs, model selection policy and maximum permissions without elevating user policy.

`WorkspaceRecord`: UUID, task/attempt IDs, canonical repository identity, owned absolute worktree path, branch ref, immutable base commit, ownership nonce/manifest, lifecycle. `VerificationEvidence`: UUID, attempt/workspace IDs, manifest/recipe version, argv and working-directory metadata (secret-safe), exit status, timeout, bounded redacted output, commit/base identity plus working-tree content fingerprint, start/end times. `ReviewFinding`: UUID, attempt ID, severity, file/path and line/range when known, actionable explanation, state `open | resolved | dismissedByHuman`, reviewer source; an LLM's absence-of-findings statement alone cannot prove the code is correct. `TaskApproval`: who approved which action, exact digest/revision and timestamp, scoped action (`executeRecipe`, `accept`, `merge`, `push`, `discardWorkspace`); it is never reused for changed content.

Store schema version 1: `projects`, `tasks`, `criteria`, `dependencies`, `agent_profiles`, `attempts`, `repository_leases`, `workspaces`, `verification_evidence`, `review_findings`, `approvals`, `task_events`. UUIDs are primary keys, dependency pairs unique, `(task_id, attempt_sequence)` unique; task updates use a version-checked transaction. One nonterminal attempt per task and one active writing lease per repository are enforced transactionally by the store, with scheduler checks as an additional guard. The repository lease records the owning attempt, generation, nonce and expiry; expiry alone never authorizes a second writer until reconciliation proves the first writer stopped. Foreign keys ON, WAL mode and transactional migrations; schema version recorded in `PRAGMA user_version`. A migration error leaves old data intact and makes board read-only with a repair/export option, never silently clears it. SQL uses bound parameters. Event payloads are typed/versioned/redacted, not raw tool output. Bounded retention retains durable state transitions, approvals and verification summaries; purge only explicit, non-active artifacts after user review.

## 5. State transitions and invariants

Allowed primary transitions: `backlog→ready` if prerequisites satisfied and configuration valid; `ready→running` only via transactional lease + workspace preflight; `running→review` only after a completed attempt and valid verification; `running→blocked` on unavailable provider, approval, rate limit, uncertain process state or verification failure; `blocked→ready` after explicit revalidation/retry; `review→done` only after all machine gates and human acceptance; `review→ready` opens a new attempt after requested changes; nonterminal→`cancelled` only when execution has been stopped/reconciled. A pause preserves the underlying status and records `pauseRequested`/`paused` on the attempt; stop and pause are distinct. `done` is immutable.

Exactly-once **claim** does not mean exactly-once external execution: persist claim and generation before dispatch; use idempotency keys when supported; otherwise reconcile process/session/workspace state before retry. All callbacks carry `(taskID, attemptID, generation)`, and late callbacks after cancel/retry are ignored. Expiring a lease marks state `blocked(uncertainExecution)` rather than blindly starting a duplicate or killing an unrelated process. Recovery must prove process ownership with nonce, executable/launch identity and workspace record before signalling; native platform authorization still applies. A physical stop should cancel provider, end owned process tree where documented and wait for confirmation; failure is visible, not silently 'cancelled'.

Scheduler orders eligible tasks by explicit priority, creation time and UUID, with topological prerequisites; default `maxWritingAttemptsPerRepository = 1`, `maxAttemptsPerTask = 3`, `maxTaskDurationSeconds = 3600` and `maxToolCallsPerAttempt = 300`. Exact budget values are defaults configurable within policy, not guarantees all providers report usage. A missing metric is `unknown`, never zero. No unbounded retry or provider fallback; retry requires an error-class-specific policy and no unresolved side effects. Human-approved actions are scoped to task + attempt + revision; they cannot be replayed across revisions.

## 6. Provider-neutral coding runtime

Introduce `CodingAgentRuntime: Sendable` with `runtimeID`, asynchronous `capabilities(configuration:)`, `start(request:) -> CodingAgentRun`, and `release(attemptID:)`; `CodingAgentRun` exposes a bounded normalized event stream and asynchronous cancellation. `CodingAgentRequest` is immutable: task/attempt/generation, role, objective, acceptance criteria, selected `SessionConfiguration`, canonical managed workspace, bounded summary and relevant files, stage, deadline and policy snapshot. Normalized events: started, text delta, activity started/updated/finished, approval requested, question asked, usage, terminal success/error. Emit exactly one terminal state; no successful completion from premature stream EOF. Runtime capability fields: textAnalysis, workspaceRead, workspaceWrite, tools, interactiveApproval, sessionResume, cancellable, structuredEvents and usageReporting. Detect capabilities per installed runtime/version and actual path, not by model name; store snapshot on attempt.

`OpenCodeCodingAgentAdapter` wraps the existing OpenCode manager and `OpenCodeProviderRuntime`/client event mapping without injecting task identifiers into global chat session IDs. Associate task attempts with distinct owned application/remote session mappings and route subagent permission events by verified ancestry/ownership. Do not repurpose an active user's chat session. Preserve managed server single-instance lifecycle: no per-task process that bypasses shutdown ownership. Ensure working directory truly points to the owned worktree; if the existing client API cannot guarantee this, fail capability/preflight rather than allowing edits in managed app data or main checkout. Confirm the endpoint and event semantics with installed OpenCode version in a live test before enabling coding dispatch.

`OpenAITextCodingAdapter` can use the existing `OpenAIProviderRuntime` for bounded text analysis and planning on explicitly supplied content. The direct Responses API path currently has no local tool executor or repository access in this app; advertise workspaceRead/workspaceWrite/tools = false. Consequently direct OpenAI cannot be chosen for independent repo review, code editing or build verification in MVP. A later shared executor could add these capabilities only with a separate audited permission design and integration tests.

CLI runtimes (Claude Code, Codex, Cursor and others) are a later **separately verified** adapter family. Before enabling each, pin supported CLI versions/protocols, validate structured event semantics, process tree ownership, working-directory isolation, cancellation and approval interception. CLI text-only output is not proof of a successful code change. Unsupported capability becomes an explicit `blocked(unsupportedCapability)`, not a silent substitution.

## 7. Workspace Manager and safety

The workspace port owns: `preflight(project, task)`, `createOwnedWorkspace(task, attempt, verifiedBase)`, `inspect`, `diff`, `reconcile`, and `retire` after explicit authorization. Use `Process` with fixed executable + argv, `shell=false`, canonical paths and no user interpolation. Root and `.git`/common-dir identity are rechecked before every mutation; reject `..`, symlinks out of allowed roots, protected branches, foreign manifests, and target paths outside approved project scope. Locate managed worktrees in a dedicated, user-authorized application-owned directory. The actual directory is chosen only after local MCP scope and native `WORKTREE_DIRTY` constraints are satisfied; no raw clone/worktree bypass.

Baseline must be a stable commit with clean source checkout, or an independently authorized immutable snapshot with a documented ownership procedure in a future milestone. Dirty/uncommitted files must never be silently copied into an attempt. Each workspace manifest contains repository identity, taskID, attemptID, base SHA and random ownership nonce. On cleanup, verify exact manifest, path and Git worktree registration; an unknown or dirty workspace remains for user inspection. No `git reset --hard`, force push, `git clean -fd`, blanket stash, direct protected-branch write or unattended merge. Worktree isolation is separate from OS sandboxing; permission policy remains applicable to terminal/network/file tools, with pre-authorized vendor tool limitations clearly displayed.

## 8. Verification and review gates

A project `VerificationRecipe` contains a versioned ordered list of structured `executable + argv + cwd + timeout`, trusted source (project CI, documented scripts, explicit user selection) and policy. Never run arbitrary model-generated shell strings or guess `npm test` from an extension. MVP recipe for this repository: `swift build --product AgenticSidebar -Xswiftc -warnings-as-errors`; `swift test -Xswiftc -warnings-as-errors`; `swift-format lint -r --strict Sources Tests` only if pinned version `604.0.0` is installed. `git diff --check` checks formatting/whitespace but does not substitute for builds. All commands run on an owned workspace, not on the dirty source tree. Node/Python/Go/Rust resolvers are separate future tested recipe plugins; inspect CI and scripts first and require explicit approval of external commands.

Evidence is valid only for exact workspace manifest, attempt ID, recipe version, commit SHA and content fingerprint. The content fingerprint hashes tracked changes plus relevant untracked source files (not ignored `.build` or generated verifier output), uses canonical relative paths and file bytes, and is captured before and after verification to detect concurrent edits. Build and tests must both exit zero, not time out and have no unknown status. Lint must pass if required by recipe; unavailable required tools block acceptance rather than skip silently. Review findings are normalized and shown as suggestions; zero Critical/High is based on a completed review record plus user disposition, not a model's unsupported assertion. Acceptance criteria need evidence or explicit user signoff per criterion. `AcceptanceGate.evaluate` returns structured reasons, never a generic Boolean that hides missing evidence. The user approves reviewed diff and current fingerprint to reach `done`; changed files invalidate approval and verification.

Merge, push and PR are separate actions with separate approvals, fresh clean status and Git ownership checks, branch protection checks and a second evidence check immediately before action. MVP collects a merge-ready review but does not perform these actions by default. No deploy or production data migrations are automated.

## 9. Native user experience

Board navigation is a new tab alongside Chat and Activity, not a replacement for existing `RootChatView` or `/goal`. Initial columns: Backlog, Ready, Running, Review, Done; Blocked is a conspicuous filter/section with reason and Resume/Retry action; Cancelled in history. Cards show title, role, provider/runtime, status and last verified time, without rendering full streams in every cell. Detail inspector shows criteria, dependency graph, immutable attempts, worktree identity, redacted activity, exact diff, verification evidence and scoped approvals. Mutating a card's status through drag/drop is forbidden in MVP; ordering Ready cards may adjust priority using a validated intent. Controls: Start, Pause, Resume, Stop, Retry, Approve Changes, Rework and Copy Report. Disable actions while pending and surface backend rejection rather than optimistic success.

Implement `TaskBoardStore` as a main-actor projection over `CodingTaskService`; store/scheduler remain non-UI actors. Updates are coalesced and bounded; only visible cards render details, preserving existing long-transcript performance. Keyboard and VoiceOver names/values/actions are required, and controls have non-color status cues. Each card links to its own task conversation, not to a reused unrelated chat session. When a backend lacks capabilities the selection UI explains why, and an unavailable provider cannot be queued as executable work.

## 10. Recovery, privacy and diagnostics

On launch open store read-only for migration check; restore tasks and events; mark previously running attempts as reconciling/blocked; inspect process identity and managed worktree; then offer verified resume. Never auto-repeat a possibly side-effectful turn. Permission requests are bound to owning task/attempt and expire on stop; reject ambiguous foreign session requests. Persistent events contain safe metadata, clipped output and artifact references, not prompts that may include secrets, token headers, environment values or private file contents. Use existing Keychain ownership; no provider secret copied into SQLite, JSON exports or telemetry. Reports distinguish verified facts, model claims, skipped checks and unavailable checks. Crash-safe writes use transactions; shutdown requests cancellation and flushes store without claiming success if children remain.

## 11. Acceptance scenarios and release gates

A1: create project/task, reject empty objective, persist and restore without losing criteria. A2: reject cycles/self edges; dependency remains blocked until prerequisite is truly done. A3: simultaneous dispatches acquire at most one writing lease; stale terminal callback cannot advance newer attempt. A4: dirty root and unauthorized worktree path block with no file mutations; another agent's tracked/untracked changes and branch are byte-identical after attempt. A5: OpenCode can launch in exact owned worktree with real event stream, correct child permission attribution, cancel and release; direct OpenAI advertises text-only and refuses tool-dependent task. A6: missing provider/rate-limit/crash and app relaunch yield honest blocked/uncertain state, no duplicate execution. A7: failed build, failed test, missing lint, outdated fingerprint, open high finding or unmet criterion all prevent done; fresh passing evidence + human acceptance permits done. A8: new content invalidates previously issued approval. A9: UI supports create/start/stop/retry/review via keyboard and VoiceOver without modifying Chat/Goal state. A10: existing `swift build`, full `swift test` and strict `swift-format` succeed on the final exact tree; native host smoke verifies process lifecycle and no orphaned owned worktree/process. A11: full audit of `git status`, diff and file hashes confirms no other agent change was overwritten, staged, committed or pushed by this feature.

Evidence classes are reported separately: unit, integration/mock, real installed OpenCode, native macOS UI, multi-language/CLI (not MVP). Passing unit tests alone is not cross-provider acceptance. No milestone may be called complete without fresh evidence at the exact tested revision.
